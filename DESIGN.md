# Концепция SIGNAL ROOM после перехода на практический формат

## Больше не квиз

Игрок входит в виртуальную рабочую среду: почта, журнал авторизации, журнал выгрузок, живые таблицы в SQLite, командные инструменты, состояние сервисов, дело с доказательствами. Пользователь может исследовать в произвольном порядке, а не выбирать один из готовых вариантов.

## Сценарий 01 — «Нарушение доверия»

Две одновременные проблемы: компрометированная сессия сервисного аккаунта приводит к подозрительным выгрузкам; новая конфигурация auth-api v2 вызывает сбои входа. Необходимо разделить эти причины, локализовать сессию, обновить реквизиты, восстановить сервис и зафиксировать подтверждающие события.

Легитимная сессия того же сервисного аккаунта — отвлекающий фактор. Бездумный отзыв чужих сессий и преждевременный перезапуск без исправления конфигурации ухудшают игровой результат. Регистрируются новые события, если локализация задерживается.

## Реализация v0.4 (полировка)

Цели и система штрафов приведены в соответствие с обязательными действиями игры. Возобновляется локальная сессия после обновления вкладки. Обновлены обработка ошибок, HTTP-защита и тесты основного сценария. Это всё ещё один вымышленный инцидент; локальный сервер и база данных не эмулируют реальную организационную сеть.

## Что уже реализовано

- Только соло.
- Свободное исследование рабочих панелей.
- Реальная учебная SQLite-база с SQL SELECT/WHERE/JOIN, read-only SQL-интерфейсом.
- Командный движок: логи, сессии, аккаунты, сервисы, улики, отчёт.
- Учебный журнал `security_events`: детектированные сигналы подмены адреса, попытки повышения привилегий, фишинга через почтовый шлюз, MAC flooding, аномалий Wi-Fi handshake и MFA fatigue; все записи содержат индикатор, оценку и защитную рекомендацию.
- Повышенная сложность: 7 целей вместо 5, шесть обязательных security-улик, четыре обязательных containment-действия, штрафы за затяжку и за containment не того сигнала.
- Стартовое меню сценария: «Все атаки» загружает весь набор сигналов; «Случайный набор» выбирает 3–6 типов заново для каждого прохождения.
- Изменение состояния при действиях, последствия ошибок, задержки.
- Итоговый отчёт и новый запуск.

## Что сознательно отложено

- Сложные ветвящиеся сценарии, эмуляция настоящей сети/контейнеров, реальные SQL UPDATE, проверка экспертом и система подсказок по уровню сложности.
- Сохранение между перезапусками сервера, облачные аккаунты и мультиплеер.
- Конфигурация пользовательских сценариев через визуальный редактор.

## План демонстрации для питча (около 90 секунд)

1. Открыть входящие и логи: заметить два независимых сигнала.
2. Через SQLite сопоставить `sessions` и `data_events`, найти конкретную подозрительную сессию.
3. Изолировать её командой, показать мгновенное изменение состояния БД.
4. Проверить `auth-api`, откатить конфигурацию, перезапустить и выполнить health-check.
5. Перейти к журналу доказательств и итоговому отчёту.

Важно: не называть движок настоящей песочницей для атак, полноценным SOC или валидированным учебным стандартом. Это локальный интерактивный прототип.
